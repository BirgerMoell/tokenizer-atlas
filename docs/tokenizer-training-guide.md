# Training a multilingual tokenizer: practical decision guide

For a model trained **from scratch**, choose the tokenizer together with the training mixture and serving architecture. A tokenizer sets the unit of the context window and the model's embedding/output vocabulary. For a model that is already trained, replacing it also changes token IDs and requires embedding/output-head adaptation and substantial continued training; intrinsic token savings alone do not justify a drop-in swap.

## What Apertus teaches

[Apertus v1](https://arxiv.org/html/2509.14233) did **not** train a new tokenizer from scratch. Its team selected the Mistral NeMo v3 Tekken byte-level BPE after comparing fertility, compression, vocabulary use and inequality on 55 FLORES+ languages. It kept a 131,072-token vocabulary and modified 47 special tokens for its use case. This is a sound baseline for a model with global language ambitions, but the choice reflects Apertus's corpus and model design.

The [Swiss AI successor experiments](https://github.com/swiss-ai/apertus-tokenizer-development) are preliminary new tokenizers. Their `preliminary_mul_200k` candidate offers better compression and a much smaller worst-language penalty on their tests than Apertus v1, at the cost of a vocabulary 53% larger than 131,072. The 131k `preliminary_mul` candidate is their fairest size-matched option. These are intrinsic results, not a demonstrated win in a fully trained Apertus v2 model. In particular, the successor's default BOS/EOS behavior differs from Apertus v1 and needs integration checks.

## Recommended workflow

1. **Write the target inventory first.** List priority languages, script variants, code-switching pairs, code, math, chat, and document formats. Define expected request shares separately from minimum service levels. Keep a broad language reserve so the merge budget is not spent solely on the largest languages.
2. **Prepare a clean, versioned tokenizer corpus.** Sample from the intended *pretraining distribution* after language identification, script checks, deduplication, boilerplate removal, and quality screening. Use language/script floors or temperature sampling to prevent the long tail from disappearing, then cap repetition so scarce low-quality text is not amplified. Swiss AI's [ablation report](https://github.com/swiss-ai/apertus-tokenizer-development/blob/main/REPORT.md) shows why composition and script grouping matter: they removed poor-script-purity and duplicate-heavy sources and tuned family weights after inspecting per-language failures.
3. **Train a small controlled matrix.** Start with byte-level BPE and a Unigram model with byte fallback as baselines; both can represent unseen text when configured correctly. Test roughly 128k and 200k/256k vocabulary budgets, holding the corpus and pretokenizer fixed when comparing sizes. Then ablate sampling weights and, if implementation maturity permits, parity-aware BPE. Do not infer from one size that an algorithm is better. [SentencePiece](https://github.com/google/sentencepiece) documents BPE/Unigram and [byte fallback](https://github.com/google/sentencepiece/blob/master/doc/special_symbols.md); the Swiss AI work compares plain BPE, parity-aware BPE, SuperBPE and Unigram.
4. **Treat pretokenization as a multilingual design decision.** Unicode letter patterns must handle combining marks (`\p{M}`), mixed scripts, apostrophes, punctuation, and whitespace. Check code identifiers and numerals separately. Cap pathological punctuation/whitespace runs to avoid using vocabulary slots on scraped separator lines. Swiss AI's [design notes](https://github.com/swiss-ai/apertus-tokenizer-development/blob/main/apertus_tokenizer_design.md) explain these choices and note that single digits versus grouped digits remains an open tradeoff. Keep normalization conservative: NFC changes exact byte-for-byte round trips for some scripts, so choose it intentionally and measure its effects.
5. **Reserve and test special tokens before pretraining.** Specify BOS, EOS, PAD, unknown/byte behavior, roles, tool boundaries and future modality tokens; pin their IDs and chat template. Test document packing and `add_special_tokens` behavior so the training pipeline does not insert duplicate BOS/EOS. The [Swiss AI candidate README](https://github.com/swiss-ai/apertus-tokenizer-development) calls out precisely this integration risk.
6. **Evaluate on held-out data before choosing.** Report tokens per UTF-8 byte and per aligned sentence for every language/script/domain, plus p50/p95/worst token cost relative to English, 2×/3× coverage, vocabulary utilization, fallback/UNK, long or junk tokens, round-trip accuracy (also after any intended normalization), and encoding throughput. Inspect the languages that lose, not only the aggregate. Use the same unmodified text across candidates. The Atlas's [FLORES benchmark](../benchmark/README.md) is one screen, not a sufficient acceptance test. Swiss AI's [production-safety report](https://github.com/swiss-ai/apertus-tokenizer-development/blob/main/REPORT_production_safety.md) provides useful examples of round-trip and vocabulary checks.
7. **Run a small model and serving ablation.** Intrinsic fertility and parity do not reliably predict downstream quality: a [controlled tokenizer study](https://arxiv.org/abs/2310.08754) found both meaningful effects and imperfect proxy metrics. Train matched small models with the same data and compute, evaluate quality by language and domain, then benchmark time to first token, output speed, memory, and completed-request cost on the intended hardware. Compare quality per compute and text per second, not perplexity per token across different tokenizers.
8. **Freeze and release reproducibly.** Version the corpus manifest, sampling weights, normalizer, pretokenizer, training code, vocabulary, special-token map, chat template, test vectors, and artifact hashes. Re-run the exact tokenizer at model-training and serving boundaries.

## Suggested first experiment for this project

Use the current 36 priority languages as a required reporting set, and a broad held-out set covering additional scripts. Train **128k and ~200k** byte-level BPE candidates on one quality-filtered, language-aware corpus; add a size-matched parity-aware candidate. Compare them with Apertus, OpenEuroLLM and the NVIDIA families already in the Atlas. Promote a candidate only if it improves the priority-language worst cases without an unacceptable English/code regression, passes production checks, and gives a favorable end-to-end model/serving result. The thresholds are decisions to set with the model team's actual language and traffic goals, not universal constants.
