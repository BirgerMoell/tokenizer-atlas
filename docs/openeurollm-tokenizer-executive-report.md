# Executive summary: tokenizer strategy for OpenEuroLLM

**Decision brief · 12 October 2026**

## Recommendation

Run two related but distinct tracks. **For the next model trained from random initialization**, compare a small set of tokenizer candidates against OpenEuroLLM's published v2 128k and 256k tokenizers before the first pretraining run, then freeze one tokenizer with the model architecture and data mixture. **For an already capable checkpoint**, keep its existing tokenizer as the default and improve target-language capability through continued pretraining and instruction tuning. Consider a small, append-only vocabulary extension only when measured token fragmentation creates a material cost or quality problem that model tuning alone does not solve. Do not substitute a newly trained tokenizer into an existing checkpoint: its token IDs and learned embedding/output rows would no longer match.

The two tracks should share a language inventory, held-out test suite, and cost model. **The primary tokenizer objective is fewer emitted tokens for the 36 target languages on representative text, while keeping other large languages efficient enough for useful deployment.** Give these groups separate acceptance gates: a good global average must not hide a target-language regression, and strong target results must not hide severe fragmentation in a large language outside the target set. Token counts are a constraint on context and compute; they are not evidence that a model understands a language.

A tokenizer has no trainable weights in the model fine-tuning sense. “Fine-tuning a tokenizer” here means either keeping its rules fixed while training the model, or changing its vocabulary and adapting the paired model. These have very different compatibility and compute costs.

## Current evidence and implication

OpenEuroLLM publishes [v2 128k](https://huggingface.co/openeurollm/tokenizer-128k-v2) and [v2 256k](https://huggingface.co/openeurollm/tokenizer-256k-v2) SentencePiece BPE artifacts. Both are trained on a reported 500 GB corpus with identity normalization and byte fallback; the 256k card describes an approximately 70% English, 7% code, 5% math, and 18% other-language mix. The language set comes from the [canonical training-data catalogue](https://github.com/OpenEuroLLM/training-data-catalogue/blob/main/languages). The v2 256k tokenizer fixed the large Georgian fragmentation seen in v1; its published 36-language FLORES mean fell from 2.43 to 1.79 tokens per whitespace word, while code remains a relative weakness against some competitors. These are tokenizer-card results, not independently reproduced model-quality results. [Source](https://huggingface.co/openeurollm/tokenizer-256k-v2)

The independent [Tokenizer Atlas benchmark](../benchmark/README.md) applies one English-relative token-cost rule to 200 aligned FLORES sentences per language/script variety. At **≤2× English**, v2 256k passes **36/36 priority languages and 95/196 broader language codes**; v2 128k passes **34/36 and 88/196**. The 196-language result reveals a tradeoff: strong priority-language coverage does not imply equally efficient global coverage. It does **not** yet answer whether specific large languages outside the target set meet a useful efficiency floor; those need their own named cohort and per-language results. Translation length and genre affect this measure; it should screen candidates, not define model support. The [live comparison](https://birgermoell.github.io/tokenizer-atlas/#coverage) includes NVIDIA, Apertus, and other baselines.

[Apertus v1](https://arxiv.org/html/2509.14233) selected and adapted the 131k Mistral NeMo Tekken tokenizer after comparing compression, fertility, vocabulary use, and language inequality. The [Swiss AI successor experiments](https://github.com/swiss-ai/apertus-tokenizer-development) test newly trained multilingual candidates; their preliminary 200k candidate improves long-tail compression in their corpus, with a 53% larger embedding/output table than a 131k option. This is a useful experiment design, not a directly transferable winner for OpenEuroLLM. A [controlled study of 24 language models](https://arxiv.org/abs/2310.08754) found that fertility and parity alone do not always predict downstream quality.

## Track A — choose a tokenizer for a new base model

**1. Lock the requirements and test set.** Use three named cohorts: **(A) the 36 target languages**, where reducing emitted tokens on representative text is the primary optimization; **(B) other large languages**, selected in advance from expected use, speaker population, available quality data, and script coverage, where each language must meet a useful minimum efficiency; and **(C) the wider multilingual long tail**, where lossless encoding and extreme-fragmentation checks remain essential. Version the language/script inventory and include code-switching, transliteration, code, math, chat, and PDF-derived text. Set acceptance thresholds before candidate selection, report each cohort and its worst performers separately, and do not allow improvements in B or C to buy a regression below A's gate. Here “more capacity for target languages” means lower observed token cost on target text; counting vocabulary pieces assigned to a language is unreliable because pieces are shared across languages.

**2. Assemble a versioned training mixture.** Use quality-filtered, deduplicated samples from the planned pretraining sources, with a manifest of source, language, script, domain, sampling weight, and license. Start from the published v2 mix as a baseline. Test sampling changes that favor target-language efficiency while reserving enough clean data for each selected large non-target language and explicit floors for low-resource languages and script families. Compare the mixes at the same vocabulary size so that a target gain and any broad-language cost are visible. Do not equalize languages blindly: repeated or mislabeled low-quality text can consume merges without improving the model. Audit the Georgian-style failure mode automatically by checking that every required language/script has actual training examples and learned pieces beyond byte fallback.

**3. Train a controlled candidate matrix.** Compare v2 128k and 256k as released. On one fixed corpus, train at least a 128k and an approximately 200k byte-level BPE candidate; include a size-matched parity-aware BPE or Unigram-with-byte-fallback candidate if the implementation is production-ready. Hold the corpus and pretokenizer fixed when testing vocabulary size; change one design choice at a time. Test Unicode combining marks, mixed-script text, digits, punctuation runs, and code identifiers. Specify normalization deliberately: OpenEuroLLM v2's identity normalization preserves exact text, whereas NFC may improve consistency but changes some byte-for-byte round trips. [Swiss AI's pretokenization study](https://github.com/swiss-ai/apertus-tokenizer-development/blob/main/apertus_tokenizer_design.md) and [SentencePiece documentation](https://github.com/google/sentencepiece) provide relevant implementation references.

**4. Gate on both intrinsic and model-level results.** On held-out, source-separated data, publish per-language tokens per byte and per aligned sentence, p50/p95/worst cost, 2×/3× coverage, byte-fallback use, vocabulary utilization, junk pieces, exact or normalization-aware round trip, and encoding throughput. Set a target-language efficiency improvement goal against v2 and a per-language regression ceiling; set separate token-cost and fragmentation ceilings for each selected large non-target language. Measure both absolute token cost and English-relative cost, since translation length can distort the latter. Validate BOS/EOS, padding, reserved IDs, chat templates, packing, and parity between training and serving libraries. Then train matched small language models under the same data and compute budget; compare downstream quality by language and domain, and measure completed-request latency, memory, and cost on target hardware. Select from the quality/coverage/cost Pareto frontier rather than the smallest mean token count.

**Decision gate:** freeze a new tokenizer only if it delivers a material, repeatable target-language advantage over the published v2 alternatives, passes the named large-language floors, and survives the small-model and serving tests. Otherwise use the v2 artifact that best fits the model's memory and language targets. Preserve the exact tokenizer files and hash with every checkpoint.

## Track B — adapt an already capable tokenizer and model

**Default: preserve the tokenizer.** If the checkpoint already encodes target text reasonably, keep its vocabulary, token IDs, normalizer, and chat template unchanged. Improve language capability with a quality-controlled multilingual continued-pretraining mixture, followed by targeted instruction tuning and evaluation. This keeps existing embeddings, serving behavior, and checkpoint compatibility intact. The model may need more target-language training exposure even where the tokenizer is efficient; training-token exposure is a separate quantity from tokens emitted per sentence.

**Escalation: append-only expansion.** If a language/script is persistently fragmented on real deployment text, run a paired A/B study: unchanged-tokenizer continued pretraining versus a small extension. Add pieces without deleting or renumbering old tokens; preserve the old normalizer and pretokenizer unless a migration and re-encoding plan exists. New pieces can still change how old text is segmented, so test old-language behavior explicitly. Select new pieces on clean target-language text and require a decomposition into old tokens. Resize both the input embedding and output projection where applicable; initialize new rows from their old-token decomposition or another tested method, then train the new rows and continue pretraining the whole model on a mixture that retains old languages. Follow with instruction tuning if needed. [In-place expansion research](https://arxiv.org/abs/2607.15232), [vocabulary-initialization evidence](https://aclanthology.org/2024.conll-1.8/), and the [Transformers resizing API](https://huggingface.co/docs/transformers/main_classes/model) support this sequence, but results on other models do not guarantee a win here.

**Reject expansion** if it regresses existing languages or tasks, cannot recover baseline quality after continued training, increases completed-request cost, or complicates tokenizer/checkpoint compatibility more than the gain warrants. A fully retrained tokenizer belongs in Track A, paired with a new base model, unless OpenEuroLLM intentionally funds a larger migration project.

## Proposed delivery sequence and ownership

| Gate | Output | Suggested project role |
|---|---|---|
| Scope | Versioned language/script inventory, deployment weights, and acceptance criteria | Data + model + evaluation leads |
| Evidence | Reproduce v2 and external baselines on a broader held-out suite; identify actual failures | Evaluation lead |
| Candidates | Fixed-corpus 128k/~200k matrix, training manifests, tokenizer safety checks | Data + tokenizer engineers |
| Model ablation | Matched small-model quality and serving cost comparison | Model + inference teams |
| Freeze or adapt | Base-model tokenizer selection; separate unchanged-tokenizer/extension decision for existing checkpoints | Joint decision gate |

**Immediate next step:** use the v2 128k and 256k artifacts as baselines, agree on a measurable target-language token-cost improvement and a named cohort of other large languages with per-language efficiency floors, then run the same held-out suite on intended code, math, chat, and document traffic. This determines whether a new tokenizer experiment or an existing-model adaptation has the stronger business case.
